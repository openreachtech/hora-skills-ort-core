# スキル

*[English](./skills.md)*

このパッケージに収録された全スキルのカタログです。各スキルに 1〜2 行の概要を添えています。

各スキルは `kit/skills/<name>/` に、スキルディレクトリの直下 1 階層で置かれます。そのフォルダ名がスキルの `name:` であり、インストール後のフォルダ名でもあります。したがって下表の **スキル** だけで足ります。`/name` として呼び出す名前、インストール後に `.claude/skills/` に現れる名前、ソースの置き場所が、すべて同じ 1 つの文字列です。先頭 3 文字ないし 4 文字の接頭辞がドメインを表します。配置と命名の規則は [ビルド規約](https://github.com/openreachtech/hora-skills-ort-core/blob/main/.claude/skills/build/SKILL.md) を参照してください。各スキルの詳細は、それぞれの `SKILL.md` と、必要なものだけがその隣に持つ `references/` にあります。1 枚で足りるスキルは `references/` を持ちません。参照を持つスキルでは、どの参照が何を定めるかを `SKILL.md` が示します。以下は領域ごとにまとめています。領域はこのカタログの見出しであり、スキル名の一部ではありません。

## 憲章

| スキル | 概要 |
| :-- | :-- |
| `hoc-charters-coding` | ORT のコーディング憲章。読みやすく統一されたコードを書く、修正を避ける、コードにすべてを説明させる。 |

## クラス

| スキル | 概要 |
| :-- | :-- |
| `hoc-classes-principles` | クラス設計の原則。プロパティを持たないクラスを作らないという大原則と、それを支える仕組み(深い不変性、コンストラクタのみ、参照＝契約)。 |
| `hoc-classes-constructor` | クラスコンストラクタの規約。コンストラクタは引数で受け取った値を保持するだけで値を決めないため、引数にデフォルト値を持たせず、既定値はファクトリメソッドが解決します。 |
| `hoc-classes-ctor` | インスタンスが自分のクラスに届くための `#get:Ctor`。定義、型のキャスト、override、名前の予約、そして `this.constructor` をそれ以外の場所に書かないこと。 |
| `hoc-classes-delegation` | 保持している、または渡された委譲先をクラスがどう使うか。委譲先の呼び出しはそれだけを本体とする `invoke~` メンバーに隔離し、失敗を結果に変えるのはそれを包む public メンバーが受け持つこと、そしてテストにその継ぎ目が要る理由。 |
| `hoc-classes-notations` | クラス本体でメンバーを書く順序。8 ブロックの配置順、getter 内・メソッド内での並び順、そしてそれらで決まらない場合にソース順へ戻すことを定義します。 |
| `hoc-classes-prohibits` | クラス定義における禁止事項。static のみのクラスと、状態(プロパティ)を持たないクラスを禁止する方針とその理由。 |
| `hoc-prohibit-native-features` | このライブラリが使わない JavaScript の言語機能。`Map`、`Object.freeze()`、ネイティブ private（`#x`、`static #x`）、decorator と、それぞれを使わない理由。 |
| `hoc-classes-inflators` | inflator(バインドメソッド)の規約。引数で渡されたクラスをバインドし、`BoundCtorRegistry` でメモ化した派生サブクラスを返すパターンと、その命名・引数。 |
| `hoc-properties` | プロパティの規約。コンストラクタ内で `this` に設定、不変(再代入禁止)、JavaScript ネイティブ private は使いません。 |
| `hoc-accessors` | アクセサ(getter/setter)の規約。不変性のため setter は禁止、getter 本体は分岐もメソッド呼び出しも持たないプロパティ参照に留めます。 |

## メンバーとスコープ

| スキル | 概要 |
| :-- | :-- |
| `hoc-manifest-pattern` | manifest パターン（別名 super strategy パターン）。構造は配線を宣言する共有オブジェクトを 1 つ持ち、その構造を成すものはすべてそれを引数に取れます。 |
| `hoc-methods` | メソッド定義の規約。名前付き引数、private メソッドへのプロパティの渡し方、ファクトリメソッドなど。 |
| `hoc-methods-recursion` | 再帰メソッドの組み方。無印の入口の後ろに private な `deep~` メンバーを置き、accumulator の初期値は入口の中で渡して、呼び出し側から渡せないようにします。 |
| `hoc-wire-dependencies` | クラスが依存先に届く経路の規約。インスタンス化する依存クラスには `[TargetClassName]Ctor` の static getter と専用のファクトリメソッド、そのまま使うモジュールには static getter を置き、サブクラスでの差し替えとテストでの置き換えを可能にします。 |
| `hoc-functions` | 関数の規約。引数はメソッドの引数に準じ、名前付き引数を原則とします。 |
| `hoc-constants` | 定数の規約。命名(大文字 `SNAKE_CASE`、enum 的オブジェクトは単数形)、chop down、オブジェクト型定数のファイル構成と配置。 |
| `hoc-contracts` | 関数・メソッドの引数と戻り値の型契約、および契約型の定義方法。 |
| `hoc-scope` | クラスメンバー間のスコープ参照。static 同士は `this` で参照し、インスタンスから static を参照する場合は `this.Ctor` を経由。`this` の分割代入は禁止。 |

## 文とスタイル

| スキル | 概要 |
| :-- | :-- |
| `hoc-statements` | 文と制御フローの規約。`let` 禁止(テストも含む)、本番コードでのリテラル `undefined` 禁止、逐次処理より高階関数、三項演算子・`if` の方針。 |
| `hoc-higher-order-functions` | `map()`、`filter()`、`reduce()`、`forEach()` の使い方。戻り値を捨てない、`forEach()` の中で代入しない、コールバックは 1 文、全要素を等しく扱い添字で取り出さない、`reduce()` は要素の中身を畳み込む、コールバックの引数の名付け。 |
| `hoc-async` | 非同期コードの規約。Promise を書くときは可能な限り `async`/`await` を使います。 |
| `hoc-errors` | エラーハンドリングの規約。値を生成するメソッドは失敗時に `null` を返すこと、および抽象メンバーが未実装を宣言する 2 つの throw — 決まった文言を載せた plain `Error` か、そのモジュールが自身の失敗のために宣言したエラークラスか。 |
| `hoc-error-codes` | エラーが載せる識別子の文字列。`Aaa.XBBB.CCC` の 3 つの部分、失敗を振り分けるカテゴリ、クライアントが上から埋める帯、および GraphQL と REST API でサーバー種別ごとに定まる `XBBB.CCC`。 |
| `hoc-coding-styles` | コーディングスタイル。式・メソッド/プロパティチェーン・関数呼び出しの引数・テンプレートリテラル・正規表現フラグの chop down(改行)位置。 |

## 命名・コメント・JSDoc

| スキル | 概要 |
| :-- | :-- |
| `hoc-naming` | 命名規約。クラス・メソッド・プロパティ・アクセサの命名、日時サフィックス(`At`/`On`、範囲は `From`/`To`)、略語基準、米国綴り、禁止語、非 ASCII 禁止。 |
| `hoc-super-prefix-method-name` | メソッド名の動詞の前に付ける super-prefix。複数件をまとめて扱う `bulk~`、再帰を担うメソッドに付ける `deep~`、委譲先のメソッドを呼ぶだけの `invoke~` と、それぞれが約束すること。 |
| `hoc-vscode-cspell` | `.vscode/cspell.json` に置くスペルチェッカーの語彙。報告された語はコードを書き換える前に `words:` か `ignoreWords:` で解決すること、正規表現などが生む語の断片は覚えさせずに無視すること、追跡対象のどこにも使われない語を外すこと、そしてチェックリストに記録する順序。 |
| `hoc-comments` | コメントは、特別な指定がない限り英語で書きます。ソースコード、生成したテスト、ドキュメントやスキルのコード例のいずれも同じです。 |
| `hoc-jsdoc` | バックエンドとフロントエンドで共通の JSDoc 記述規約。型アノテーション、右辺で禁じられるキャストとサードパーティ限定の例外、`@typedef`、型のみインポート、およびブロック自体のレイアウトを定義し、Vue/Nuxt 固有の規約は参照ファイルにまとめています。型検査器が報告したエラーを消すのもこのスキルです。 |
| `hoc-type-errors` | 型検査器の報告を、何を直すか決める前にどう読むか。キャストがエラーを黙らせている間は報告された件数が作業量を表さないこと、およびエラーが指しているのは欠けた注釈ではなく誤った値かもしれないことを定義します。 |

## git

| スキル | 概要 |
| :-- | :-- |
| `hoc-git-branch` | リポジトリが持つブランチの規約。名前で決まる 5 本のトランクとその役割が課すもの、flow ごとに `main` から切ってよいもの、一般ブランチの命名、トランクを開く空のマーカーコミット、サブブランチを閉じる `--no-ff` マージとその件名、rebase が必ず取る `-r`、そしてブランチがまだ何かを持っているか、捨ててよいかを見分けるもの。 |
| `hoc-git-commit` | コミットの規約。1 コミットに含める粒度、メッセージ形式(命令形 / Conventional Commits をプロジェクト単位で選択)、両者で共通の動詞語彙。 |
| `hoc-git-commit-order` | コミットを並べる順序。最初のコミットでテストを赤にする（足すならテストが先、消す・上限を下げるなら実装が先）。そのあとは振る舞い、構造、追加の順。 |
| `hoc-git-push` | push を行う前に要るもの。1 回ごとに要る許可とその狭さ、ここでは実行せず人に渡す force-push、remote を読んだ結果を根拠に可否が決まる操作をその読み取りごと人に渡すこと、設定に頼らず remote とブランチを明示すること、そしてタグと remote ブランチの削除を手で push しない理由。 |

## 依存と公開

| スキル | 概要 |
| :-- | :-- |
| `hoc-npm-adopt-tool` | サードパーティ製ツールをそもそも導入してよいかを定める。導入の理由として通るものと通らないもの、install 前に tarball を精査する監査、そのツールを名指すモジュールをひとつに閉じるラッパー。導入後の版の移動は `hoc-npm-raise-deps` のもの。 |
| `hoc-npm-categorize-deps` | パッケージをマニフェストのどの欄に宣言するかを定める。peer が買うもの、両者の範囲が食い違ったときにパッケージマネージャが何をするか、そして 2 本目のコピーがなぜ設計で避けるべき失敗なのか。宣言済みの版を動かすのは `hoc-npm-raise-deps` のもの。 |
| `hoc-npm-install-scripts` | install スクリプトの実行を許可制で決める仕組み。deny を既定とすること、設定を先に置いて install を後にする順序、スクリプトの有無を実行せずに報告する dry run。 |
| `hoc-npm-npmrc` | npm の設定ファイル `.npmrc` の書き方。各設定は `=` の両側に空白を置いた `key = value` で書き、`npm config set` は使わず直接編集する。各設定の意味は、それを有効にする規約の担当です。 |
| `hoc-npm-vulnerability` | 脆弱な版を入れないための規約。audit が見るものと見ないもの、公開日数による検疫とそれが効かないインストール、推移的依存だけを引き上げて報告を解決する方法、修正版のない報告の判断。 |
| `hoc-npm-publish` | リリースにおける version bump のコミット位置と、それが最後でなくなったときの扱い。公開前に tarball を読むことは `hoc-npm-publish-audit`、リリースが取り込む依存バージョンを動かすことは `hoc-npm-raise-deps` の担当です。 |
| `hoc-npm-publish-audit` | パッケージが出ていく前の最後の読み取り。allowlist ではなく `npm pack` が出力する inventory、空のプロジェクトに tarball をインストールして使うこと、CI が走らせるインストール、同時に出すパッケージ同士の inventory の差分、読み手と同じ手順でたどる README、linter が見ない規約、そして何を読み何を読まなかったかを明示し、直すべきものの一覧と、記号で示す判定で締める報告。リリース自身のコミットの順序は `hoc-npm-publish` の担当です。 |
| `hoc-npm-raise-deps` | 宣言済みの依存バージョンを、各レンジが既に許す最新版まで引き上げる規約。レンジの外にある major は対象外とし、パッケージごとの別判断に回します。lockfile ではなく宣言レンジを突合すること、版の移動を暗黙の update ではなくマニフェストへ書き下すこと、新しい版が別の registry へ移ったパッケージを入れ直すこと、そしてパスを閉じる一度の install と一つの lockfile コミット。 |
| `hoc-dependency-defect` | 自分が所有していないコード(パッケージなど)の不具合への対処。壊れているメンバーだけを override するサブクラスを作り、自分の名前で呼び出し、いつ削除できるかをコメントに残します。 |
| `hoc-eslint-config` | 共有 ESLint config と手元の `eslint.config.js`。版上げでどの版を取るか、判断なしに直してコミットできる範囲と止めて報告する範囲、ルールのオプションをファイル指定で差し引く方法、そしてコードではなくルールを緩めてよい条件。 |

## ドキュメント

| スキル | 概要 |
| :-- | :-- |
| `hoc-readme` | プロジェクトが持つ README。言語ごとに持つファイル、セクションの並び順と各セクションの定型文、`docs/` へ切り出して貼り戻すリンク、API リファレンス、コード例の命名。 |
| `hoc-license` | プロジェクトが持つ `./LICENSE`。`package.json` の `license` フィールドが決めます。値ごとに入る本文、差し込むプレースホルダ、`UNLICENSED` が求める削除、そしてフィールドが無いときの扱い。 |
| `hoc-boilerplate` | すべてのクローンが持ち回る `about-boilerplate.md` の規約。ボイラープレート自身では動き、そこからクローンしたリポジトリでは凍結される `## Version`、リリースを閉じる 1 コミットの版上げ、そして 3 箇所に書かれた版を一致させる検査。 |
| `hoc-documentation` | ドキュメント記述の規約。文書が事実として書いてよい範囲と、書く代わりに読者を辿らせるべきもの、変更が動かした事実に文書をどう追従させるか、読者向けに生成する文書を何語で書くか、およびドキュメント内でクラスメンバーを参照する際の `#instanceMember` / `.staticMember` 記法などを定義します。 |
| `hoc-resolve-shorthand` | 短い handle を、読者が出会ったその場で解けるようにする規約。ラベルを発明せず既存の名前を書くこと、phase 番号や issue 番号が伴うべき中身、依頼者へ差し戻す一覧が各行に添える出所、そしてどこまで書けば足りるか。 |
| `hoc-requirement-definition` | 曖昧な依頼を、依頼者との対話を通じて要件定義書にします。要件・観測可能な受入基準・スコープ外リスト・未決事項をまとめます。 |
| `hoc-deployment-document` | 対話でサーバーデプロイ手順書を書き起こします。ホスティングとプロセス管理の構成、初回構築、定常リリース、マイグレーション、切り戻し、そして各手順が成功したことを確認できる出力。 |
| `hoc-implementation-progress` | 進行中の実装状況を、要件 ID に紐づけた進捗ドキュメントで可視化します。ステータスは記録された根拠に基づいてのみ前進させます。 |
| `hoc-skill-updating` | スキル(`SKILL.md`)の新規作成・更新の規約。命名、どのライブラリに属するか、どこでそのスキルが終わり隣の規約が引き継ぐか、平坦なディレクトリ構成、記述時の作法を定義します。 |

## レビューとワークフロー

| スキル | 概要 |
| :-- | :-- |
| `hoc-code-review` | 変更をコードレベルで読み取り専用にレビューし、仕様適合性・正当性・規約準拠についての所見レポートを出します。修正は一切しません。 |
| `hoc-workflows` | 開発ワークフローの手続き規約。実装の進め方、規約と周囲のコードが食い違うときにどちらへ従うか、コミット前・完了前に必ず行う手順を定義します。 |
| `hoc-retake-declaration` | 呼び出し側から見えるものを動かさずに既存コードを作り直す方法。retake は gain を主張しないので、ロジックは呼び出し側が既に届いているメンバーに残し、足した引数は既定値を持ち、途中で見つけた欠陥は直さずに報告します。 |

## 導入

```sh
npm install -D @openreachtech/hora-skills-ort-core
npx --no hora-skills-ort-core install
```

`postinstall` フックの宣言、複数ドメインを同じ `.claude/skills/` に入れる方法、配置を最新に保つ方法は [README](https://github.com/openreachtech/hora-skills-ort-core/blob/main/README.ja.md) にあります。
